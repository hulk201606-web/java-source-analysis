# 分布式一致性哈希 vs 哈希环源码级深度对比

> **面试权重**：⭐⭐⭐⭐⭐（分布式存储/缓存/消息队列核心算法）  
> **核心参考**：Memcached 一致性哈希（2001 发明）+ Ketama 改进 + CHD（2014）  
> **面试必背**：普通哈希 → 一致性哈希 → 虚拟节点 → Ketama → CHD

---

## 一、为什么需要一致性哈希

```
┌─────────────────────────────────────────────────────────────┐
│  ★ 普通哈希（取模）的问题：节点变动时大面积缓存失效          │
│                                                               │
│  普通哈希：hash(key) % N （N = 节点数）                       │
│                                                               │
│  例子：3 个节点 → 4 个节点（新增 1 个节点）                   │
│                                                               │
│  hash(key) % 3 → hash(key) % 4                               │
│  所有 key 的映射关系都变了！                                  │
│  → 原来在 Node1 的 key 现在可能到 Node3                     │
│  → 原来缓存有 → 现在没有 → 全部回源 DB                       │
│  → DB 被打爆（缓存雪崩！）                                   │
│
│ ★ 一致性哈希解决的问题：                                      │
│   节点变动时，只需要重映射 **1/N** 的 Key                    │
│   → 90% 以上的 Key 保持原映射 → DB 压力可控                │
│
│ ★ 面试高频：哪些系统用一致性哈希？                             │
│   Memcached（原生）+ Redis Cluster（哈希槽）+ Rendezvous     │
│   Hash（TiKV PD）+ Dubbo（负载均衡）+ gRPC（XDS）            │
│
└─────────────────────────────────────────────────────────────┘
```

## 二、一致性哈希环源码级

### 2.1 核心思想

```
┌─────────────────────────────────────────────────────────────┐
│  ★ 一致性哈希环核心（面试必背！）                              │
│                                                               │
│  ① 把所有哈希值（0 ~ 2^32-1）围成一个环                      │
│  ② 每个节点 hash(node_name) → 映射到环上一个点               │
│  ③ 每个 key hash(key) → 沿顺时针方向找到第一个节点           │
│
│  图示：                                                       │
│                                                               │
│              Node A (hash=1000)                               │
│             ↗                 ↘                               │
│     Key 1 (hash=500)          Key 2 (hash=1500)              │
│        → Node A                  → Node B                    │
│              ↖                 ↙                               │
│              Node C (hash=3000) ← Node B (hash=2000)         │
│
│  新增 Node D (hash=2500)：                                    │
│  原来：Key(hash 2001-3000) → Node C                          │
│  现在：Key(hash 2001-2500) → Node B ← 没变！                 │
│        Key(hash 2501-3000) → Node D ← 迁移过来              │
│        Key(hash 0-1000) → Node A ← 没变！                    │
│        Key(hash 1001-2000) → Node B ← 没变！                 │
│
│  → 只有 2501-3000 这段的 Key 从 C 移到 D                      │
│  → 只有约 1/N 的 Key 受影响！                                 │
│
└─────────────────────────────────────────────────────────────┘
```

### 2.2 基础实现

```java
// ★ 一致性哈希环基础实现（源码级）
```

## 三、虚拟节点（解决数据倾斜）

### 3.1 为什么需要虚拟节点

```
┌─────────────────────────────────────────────────────────────┐
│  ★ 一致性哈希的问题：数据倾斜                                │
│                                                               │
│  3 个节点在环上分布不均：                                      │
│  Node A hash=1000                                             │
│  Node B hash=2000（紧跟 A，占很少空间）                       │
│  Node C hash=4000                                             │
│
│  环上空间：                                                   │
│  A→B: 1000        （占 ~25%）                                │
│  B→C: 2000        （占 ~50%）← Node C 管了一半的 Key！      │
│  C→A: (2^32-4000+1000)（占 ~25%）                            │
│
│  → Node C 压力是 A 和 B 的 2 倍！                             │
│  → 严重数据倾斜！                                             │
│
│ ★ 虚拟节点解决倾斜：                                          │
│  每个物理节点映射到环上 **N 个虚拟节点**（N=150 推荐）        │
│  hash(node_name + "#" + i) → 环上多个点                      │
│
│  3 物理节点 × 150 虚拟节点 = 450 个点在环上均匀分布           │
│  → 每个物理节点管 ~1/3 的 Key（几乎均匀）                    │
│
└─────────────────────────────────────────────────────────────┘
```

## 四、Ketama（Memcached 官方方案）vs 原始一致性哈希

```
┌─────────────────────────────────────────────────────────────┐
│  ★ Ketama = Memcached 官方一致性哈希方案（2005）              │
│                                                               │
│  原始一致性哈希问题：                                          │
│   ① 哈希算法选择（MD5 太慢？CRC32 碰撞多？）                  │
│   ② 虚拟节点数量怎么选？                                      │
│   ③ 节点权重（不同节点容量不同）                             │
│
│  Ketama 统一解决：                                            │
│   ① 用 MD5 做基础哈希（均匀、成熟）                           │
│   ② 每个物理节点 160 个虚拟节点（固定）                       │
│   ③ 支持权重（weight 参数）                                  │
│
│ // Ketama 实现（简化）                                        │
│ public class KetamaRing {                                     │
│     private TreeMap<Long, String> ring = new TreeMap<>();     │
│     private static final int VNODE_PER_NODE = 160;            │
│
│     public void addNode(String nodeName, int weight) {        │
│         // weight=2 → 生成 160*2=320 个虚拟节点              │
│         int vnodes = VNODE_PER_NODE * weight;                 │
│         for (int i = 0; i < vnodes; i++) {                    │
│             // Ketama 用 MD5 生成 4 组 hash                   │
│             byte[] digest = md5(nodeName + "-" + i);          │
│             for (int j = 0; j < 4; j++) {                     │
│                 long h = ((digest[3+j*4] & 0xFF) << 24) |    │
│                         ((digest[2+j*4] & 0xFF) << 16) |    │
│                         ((digest[1+j*4] & 0xFF) << 8)  |    │
│                         ((digest[j*4] & 0xFF));               │
│                 ring.put(h & 0xFFFFFFFFL, nodeName);          │
│             }                                                 │
│         }                                                     │
│     }                                                         │
│ }                                                             │
│
│ ★ 面试高频：Ketama vs 原始一致性哈希？                        │
│   原始：简单、灵活、自己选参数；Ketama：固定参数、支持权重、官方推荐│
│
└─────────────────────────────────────────────────────────────┘
```

## 五、Rendezvous Hash（HRW）— TiKV PD 用的方案

```
┌─────────────────────────────────────────────────────────────┐
│  ★ Rendezvous Hash = Highest Random Weight（HRW，1996）       │
│                                                               │
│  核心：对每个 key，计算 key 与每个节点的 hash，选最大的      │
│                                                               │
│  hash(key + node1) = 0.89                                    │
│  hash(key + node2) = 0.12                                    │
│  hash(key + node3) = 0.45                                    │
│  → 选 node1（hash 最大）                                     │
│
│  ★ 优点：                                                     │
│   ① 实现超简单（不需要哈希环、不需要虚拟节点）                │
│   ② 节点变动只影响 1/N 的 Key（和一致性哈希一样）            │
│   ③ 不需要排序（TreeMap 都不用）                              │
│
│  ★ 缺点：                                                     │
│   每次 getKey() 都要对所有节点算 hash（O(N)）               │
│   → 节点多了（比如 1000 个）性能下降                         │
│   → 适合节点数较少的场景（TiKV PD 节点数不会太多）           │
│
│ // HRW 实现                                                   │
│ public class RendezvousHash {                                 │
│     private List<Node> nodes = new ArrayList<>();             │
│
│     public Node getNode(String key) {                          │
│         Node bestNode = null;                                 │
│         double bestScore = -1;                                │
│         for (Node node : nodes) {                             │
│             // hash(key + node.name) → score                  │
│             double score = score(hash(key + node.getName()));  │
│             if (score > bestScore) {                          │
│                 bestScore = score;                            │
│                 bestNode = node;                              │
│             }                                                 │
│         }                                                     │
│         return bestNode;                                      │
│     }                                                         │
│
│     // 把 hash 转成 [0, 1) 均匀分布                           │
│     private double score(long h) {                            │
│         return (Math.abs(h) + 1) / ((double) Long.MAX_VALUE + 1); │
│     }                                                         │
│ }                                                             │
│
│ ★ 一致性哈希 vs HRW 对比表（面试最高频！）：                   │
│  ┌──────────┬──────────────┬──────────────┐                 │
│  │ 维度       │ 一致性哈希环  │ Rendezvous Hash │              │
│  ├──────────┼──────────────┼──────────────┤                 │
│  │ 数据结构    │ TreeMap      │ List          │              │
│  │ 查询复杂度  │ O(log N)     │ O(N)          │              │
│  │ 实现复杂度  │ 中（需虚拟节点）│ 低（不需虚拟节点）│          │
│  │ 节点变动影响│ ~1/N         │ ~1/N          │              │
│  │ 典型应用    │ Memcached    │ TiKV PD       │              │
│  │            │ Redis Cluster │ AWS ALB       │              │
│  │            │ Dubbo        │               │              │
│  └──────────┴──────────────┴──────────────┘                 │
│
└─────────────────────────────────────────────────────────────┘
```

## 六、面试考点（22 题）

| # | 考点 | 答案 |
|---|------|------|
| 1 | 为什么需要一致性哈希？| **普通哈希取模 N 时，节点变动所有 Key 映射都变** → 缓存雪崩；一致性哈希只影响 1/N 的 Key |
| 2 | 一致性哈希环核心？| **把哈希值围成环 + 节点 hash 映射到环上 + key 顺时针找第一个节点** |
| 3 | 数据结构？| **TreeMap（红黑树）** + ceilingEntry() 找下一个节点 |
| 4 | 虚拟节点作用？| **解决数据倾斜**；每个物理节点 → N 个虚拟节点（推荐 150）→ 均匀分布 |
| 5 | 虚拟节点数量？| **150 推荐**；太少倾斜，太多占内存 |
| 6 | Ketama 是什么？| Memcached 官方方案；**固定 160 vnode + MD5 + 支持权重** |
| 7 | Rendezvous Hash（HRW）？| 对每个 key 计算 key+node 的 hash → 选最大的；**O(N) 查询 + 不需要环 + 不需虚拟节点** |
| 8 | 一致性哈希 vs HRW？| 一致性哈希：TreeMap O(logN) + 虚拟节点；HRW：List O(N) + 不需虚拟节点 |
| 9 | 哈希算法选择？| FNV-1a（快）+ MD5（均匀）+ XXHash（最快）；避免 MD5/SHA-256 太慢 |
| 10 | Redis Cluster 用什么？| **哈希槽**（16384 个槽 + CRC16 取模）→ 一致性哈希变种 |
| 11 | Dubbo 负载均衡？| **ConsistentHashLoadBalance**（一致性哈希）+ Random + RoundRobin |
| 12 | 面试最高频考点排序？| **1. 为什么需要一致性哈希 2. 哈希环核心 3. 虚拟节点 4. Ketama vs HRW 5. 普通哈希 vs 一致性哈希** |
| 13 | 学习路径？| TreeMap ceilingEntry → 虚拟节点 → Ketama MD5 4 段 → Rendezvous Hash → Redis Cluster 哈希槽 |
| 14 | 面试常见追问？| 节点变动影响比例？→ ~1/N；虚拟节点太少会怎样？→ 倾斜严重 |
| 15 | TiKV PD 用什么？| **Rendezvous Hash（HRW）**；节点数少 → O(N) 没问题 |
| 16 | gRPC 负载均衡？| 支持 RingHash + XDS；RingHash 是一致性哈希 |
| 17 | Redis Cluster 哈希槽？| 16384 槽 → CRC16(key) % 16384；槽迁移类似一致性哈希 |
| 18 | 2024 新方案？| **CHD（2014）** 比 HRW 快 10x；**Jump Hash（Google 2014）** 极简实现 |
| 19 | 面试高频场景？| Memcached 集群 + Redis Cluster 扩容 + TiKV PD Region 调度 |
| 20 | 权重怎么实现？| Ketama：weight × 160 vnodes；自己实现：环上增加更多虚拟节点 |
| 21 | 为什么 TiKV PD 用 HRW 不用一致性哈希？| PD 节点数少（一般 < 100）→ O(N) 没问题；HRW 实现简单且不需要维护环 |
| 22 | 面试最高频陷阱？| 一致性哈希 + 虚拟节点 = **标准答案**；只说一致性哈希（不提虚拟节点）会被追问倾斜问题 |
