> **面试权重**：⭐⭐⭐⭐⭐（分布式系统基础理论，高频必问）  
> **核心参考**：Eric Brewer CAP / Abadi PACELC / Gilbert Lynch CAP 证明

## 一、CAP 经典三选二

```
┌─────────────────────────────────────────────────────────────┐
│  ★ CAP 定理（Eric Brewer 2000 PODC）                       │
│                                                               │
│  分布式系统三属性不可兼得：                                   │
│                                                               │
│  C (Consistency)   一致性                                    │
│  ─────────────────────────                                   │
│  所有节点同一时刻看到相同数据                                  │
│  写成功后，读一定读到最新版本                                 │
│  → "线性一致"或"可序列化一致"                                │
│                                                               │
│  A (Availability) 可用性                                     │
│  ─────────────────────────                                   │
│  每个请求都能在**有限时间内**得到非错误响应                    │
│  → 不保证返回最新数据（返回旧数据也算可用）                  │
│                                                               │
│  P (Partition Tolerance) 分区容错                           │
│  ─────────────────────────                                   │
│  即使网络分区（节点间无法通信），系统仍能工作                  │
│  → 网络分区在分布式系统中**必然发生**（硬件故障/延迟/丢包） │
│  → 所以实际上 P 是必选项！                                   │
│                                                               │
│ ★ 核心结论（面试必答！）：                                   │
│   P 必选（网络不可靠 → 分区必然发生）                       │
│   → 只能 C + A 二选一！                                      │
│   → CAP 实际是 **CP vs AP 的选择**                          │
│
└─────────────────────────────────────────────────────────────┘
```

### 1.1 CP vs AP 选择（面试最高频）

```
┌─────────────────────────────────────────────────────────────┐
│  ★ CP 系统（选择一致性，牺牲可用性）                        │
│                                                               │
│  什么时候选 CP？                                              │
│  → 数据绝对不能错（金融/支付/账户余额）                      │
│  → 宁可短时间不可用，也不能数据不一致                        │
│                                                               │
│  CP 系统有哪些？                                              │
│  ┌──────────┬──────────────┬──────────────┐                 │
│  │ 系统       │ 一致性协议    │ 说明          │                 │
│  ├──────────┼──────────────┼──────────────┤                 │
│  │ TiKV      │ Raft + Percolator│ 分布式事务    │                 │
│  │ ETCD      │ Raft        │ K8s 元数据     │                 │
│  │ Nacos Config │ JRaft    │ CP 配置模式    │                 │
│  │ ZooKeeper │ ZAB         │ CP 锁 + 元数据 │                 │
│  │ Google Spanner │ Paxos+2PC │ CP 事务    │                 │
│  │ MongoDB（单分片）│ Raft  │ 强一致读写    │                 │
│  └──────────┴──────────────┴──────────────┘                 │
│                                                               │
│  CP 系统在网络分区时怎么表现？                                │
│  → 少数派节点停止服务（无法过半 Commit）                     │
│  → 多数派节点继续服务（过半 Commit）                         │
│  → 自动选主 + 数据一致                                       │
│  → 代价：网络分区期间少数派**不可用**（返回错误）            │
│
│  ─────────────────────────────────────────────────────────  │
│                                                               │
│  ★ AP 系统（选择可用性，牺牲一致性）                        │
│                                                               │
│  什么时候选 AP？                                              │
│  → 数据可以短暂不一致（服务发现/社交动态）                    │
│  → 宁可返回旧数据，也不能不可用                              │
│                                                               │
│  AP 系统有哪些？                                              │
│  ┌──────────┬──────────────┬──────────────┐                 │
│  │ 系统       │ 一致性协议    │ 说明          │                 │
│  ├──────────┼──────────────┼──────────────┤                 │
│  │ Nacos Naming │ Distro  │ AP 服务发现    │                 │
│  │ Eureka     │ Gossip       │ AP 服务发现    │                 │
│  │ Redis Cluster │ Hash Slot │ 最终一致集群 │                 │
│  │ Cassandra  │ Quorum       │ AP + tunable  │                 │
│  │ DyanmoDB   │ Quorum       │ AP 可选强一致 │                 │
│  │ Riak       │ Quorum       │ AP           │                 │
│  └──────────┴──────────────┴──────────────┘                 │
│                                                               │
│  AP 系统在网络分区时怎么表现？                                │
│  → 所有节点继续服务（不分多数派少数派）                      │
│  → 写入本地 + 异步复制（Gossip/Distro）                      │
│  → 网络恢复后 → 自动修复（CRDT/Last-Write-Wins）             │
│  → 代价：网络分区期间**数据可能不一致**                      │
│
└─────────────────────────────────────────────────────────────┘
```

## 二、CAP 常见误区（面试高频踩坑点）

### 2.1 "选 CA"——大错特错

```
┌─────────────────────────────────────────────────────────────┐
│  ★ 面试踩坑：有人说"选 CA，不选 P"——完全错误！              │
│                                                               │
│  为什么 P 是必选项？                                          │
│  Eric Brewer 论文原文：                                      │
│  "In a distributed system, partition tolerance is a given." │
│  "You can't choose not to have partitions."                  │
│                                                               │
│  工程事实：                                                   │
│  硬件：网卡故障 / 交换机故障 / 光纤断                       │
│  软件：进程 GC 暂停 / 容器 OOM / 网络延迟                    │
│  运维：误配置防火墙 / 大促流量洪峰                           │
│  → 网络分区**必然发生**，不可避免                            │
│  → 所以你**不能不选 P**                                      │
│                                                               │
│  单机为什么能"选 CA"？                                        │
│  单机没有网络分区 → CAP 不适用                               │
│  单机 ACID 是 CAP 不适用场景                                 │
│  → 别用单机 ACID 举例说 CAP 三选二不对                      │
│
└─────────────────────────────────────────────────────────────┘
```

### 2.2 "2/3 投票 = CP"——错误（可能 C 不够强）

```
┌─────────────────────────────────────────────────────────────┐
│  ★ 面试踩坑："TiKV 3 节点，2/3 投票 = CP"——不完全对！       │
│                                                               │
│  CP 有不同强度：                                              │
│  ① Linearizable（线性一致，最强）：                          │
│     写后读一定读到最新（类似单机顺序执行）                    │
│     TiKV Lease Read + Raft 可以做到                          │
│
│  ② Sequential（顺序一致）：                                  │
│     所有操作按全局序号执行                                    │
│
│  ③ Causal（因果一致）：                                      │
│     有因果关系的操作按顺序（社交动态）                        │
│
│  ④ Monotonic Read（单调读）：                                │
│     同一个客户端越读越新（但不同客户端可以不同）              │
│
│ ★ TiKV Raft 的一致性强度（面试高频）：                      │
│   写：Linearizable（Raft Commit 保证）                       │
│   读：Lease Read = Linearizable；ReadIndex = Sequential；    │
│        默认本地读 = Monotonic Read                          │
│   → TiKV 默认 Lease Read 最强！                             │
│
│ ★ 不要把"CP"等同于"绝对强一致"                              │
│   CP 是选了一致性（非 AP）但一致性可以有不同强度            │
│
└─────────────────────────────────────────────────────────────┘
```

### 2.3 "AP 系统不保证数据正确"——半对半错

```
┌─────────────────────────────────────────────────────────────┐
│  ★ 面试踩坑："AP 系统不保证数据正确"——不完全对！            │
│                                                               │
│  AP 系统的"最终一致"可以很强：                                │
│  ① Cassandra 可调一致性（Quorum + Q + W）：                 │
│     W + R > N → 强一致（虽然底层是 AP）                     │
│     W + R <= N → 最终一致                                    │
│     → 可以根据业务灵活调整                                   │
│
│  ② Nacos Naming Distro：                                    │
│     最终一致 + 几秒钟收敛 → 实际上够用（服务发现）          │
│     → 数据不会丢，只是短暂有旧数据                          │
│
│  ③ Redis Cluster（Hash Slot）：                              │
│     MOVED 重定向保证一致性（客户端重试到正确节点）           │
│     → 虽然底层是 Hash Slot，但通过客户端重定向保证强一致     │
│
│  ★ AP 系统也可以做到"足够强的一致性"——只是不是 CP 的硬保证  │
│
└─────────────────────────────────────────────────────────────┘
```

## 三、PACELC：CAP 的真实世界版本

### 3.1 PACELC 核心思想

```
┌─────────────────────────────────────────────────────────────┐
│  ★ PACELC（Daniel Abadi 2012 论文）——CAP 的真实世界版本    │
│                                                               │
│  CAP 只说网络分区时 C+A 二选一                               │
│  但**无网络分区时**系统怎么选？CAP 没说！                    │
│                                                               │
│  PACELC 完整覆盖两种场景：                                    │
│                                                               │
│  网络分区时（Partition 存在）：                               │
│    C vs A → 二选一（CAP 传统结论）                           │
│                                                               │
│  无网络分区时（Partition 不存在）：                           │
│    L (Latency) vs C → 二选一（新发现！）                     │
│    → 不牺牲 A（可用性），牺牲的是延迟                       │
│    → 要强一致 → 同步复制（慢，ms 级延迟）                   │
│    → 要低延迟 → 异步复制（快，us 级延迟）                   │
│
│  ★ PACELC = PA (Partition + Availability) + CE (Consistency │
│  vs Eventual consistency) + LC (Latency vs Consistency)    │
│                                                               │
│  → 完整覆盖了分布式系统的一致性选择：                        │
│  1. 网络分区 → C vs A                                        │
│  2. 正常运行 → C vs L                                        │
│
└─────────────────────────────────────────────────────────────┘
```

### 3.2 TiKV vs Nacos vs Cassandra PACELC 分析

```
┌─────────────────────────────────────────────────────────────┐
│  ★ PACELC 实战分析（面试高频！）                            │
│                                                               │
│  TiKV（Raft + Percolator）：                                  │
│  网络分区时：选 C，少数派停止服务（CP）                     │
│  正常运行时：选 C（同步复制），牺牲 L（每个写 20-50ms）    │
│  → TiKV 默认 C 优先（强一致 + 较低延迟）                   │
│  → TiKV Lease Read：读走本地（L 优先，牺牲一点 C）         │
│
│  Nacos Config（JRaft）：                                      │
│  网络分区时：选 C，少数派停止服务（CP）                     │
│  正常运行时：选 C（同步复制），牺牲 L                       │
│  → 和 TiKV 一样（JRaft 也是同步复制）                       │
│
│  Nacos Naming（Distro）：                                     │
│  网络分区时：选 A，所有节点继续服务（AP）                   │
│  正常运行时：选 L（异步 Gossip，极快），牺牲 C（最终一致）  │
│  → 正常运行几乎看不到不一致，极快 + 极可用                  │
│
│  Cassandra（Quorum）：                                        │
│  网络分区时：可调（W+R>N 强一致 / W+R<=N 最终一致）        │
│  正常运行时：选 L（异步复制），牺牲 C                       │
│  → 可调灵活性最高                                            │
│
│  Redis Cluster（Hash Slot）：                                │
│  网络分区时：选 C（MOVED 重定向）                           │
│  正常运行时：选 L（异步复制），牺牲一点 C（异步同步）        │
│  → Redis Cluster 主从复制是异步的                            │
│
└─────────────────────────────────────────────────────────────┘
```

## 四、CAP + PACELC 全景决策树

```
┌─────────────────────────────────────────────────────────────┐
│  ★ 分布式系统一致性决策树（面试必备！）                       │
│                                                               │
│  你的数据能短暂不一致吗？                                     │
│  ┌────────────────────┬────────────────────┐                │
│  │ 能                 │ 不能               │                │
│  └────────┬───────────┴────────┬───────────┘                │
│           ↓                    ↓                             │
│        选 AP                 选 CP                          │
│        Distro/               Raft/ZAB/Paxos                │
│        Gossip/Quorum                                         │
│           ↓                    ↓                             │
│        正常运行？           正常运行？                       │
│        ↓↓↓↓                ↓↓↓↓                            │
│        L 优先（快）         C 优先（同步复制）              │
│        异步复制             但 TiKV Lease Read = L 优先读  │
│        最终一致             Nacos Config = C 优先（JRaft）  │
│                                                               │
│  → TiKV 写：CP + C 优先（同步复制）                          │
│  → TiKV 读：CP + L 优先（Lease Read，本地读）                │
│  → Nacos Config：CP + C 优先（JRaft 同步复制）               │
│  → Nacos Naming：AP + L 优先（Distro 异步 Gossip）           │
│
└─────────────────────────────────────────────────────────────┘
```

## 五、面试考点（20 题）

| # | 考点 | 答案 |
|---|------|------|
| 1 | CAP 三属性？| **C（一致性：所有节点同一时刻看到相同数据）/ A（可用性：请求能在有限时间内得到非错误响应）/ P（分区容错：网络分区时系统仍能工作）** |
| 2 | CAP 核心结论？| **P 必选**（网络分区必然发生）→ 只能 **C+A 二选一** |
| 3 | CP vs AP 系统？| **CP（TiKV/ETCD/Nacos Config/ZK）：网络分区时少数派不可用，数据一致**；**AP（Nacos Naming/Eureka/Cassandra）：网络分区时所有节点继续服务，数据最终一致** |
| 4 | 为什么不能选 CA？| **P 必选**（网络不可靠，分区必然发生）；单机 ACID 不适用分布式 CAP |
| 5 | PACELC 是什么？| **CAP + 无分区时的 C vs L**；网络分区：C vs A；无分区：C vs L（要强一致同步复制慢，要低延迟异步复制快）|
| 6 | PACELC 核心思想？| CAP 只说了网络分区时的选择；PACELC 补充了**正常运行时的 C vs L**（新发现！） |
| 7 | TiKV PACELC 分析？| **网络分区：CP（少数派不可用）**；**正常运行：C 优先（同步复制 20-50ms）**；读走 Lease Read 时 L 优先（本地读 ~1ms）|
| 8 | Nacos PACELC 分析？| **Config：CP + C 优先（JRaft 同步）**；**Naming：AP + L 优先（Distro 异步 Gossip）** |
| 9 | Cassandra 可调一致性？| **W+R>N 强一致**；**W+R<=N 最终一致**；可根据业务灵活调整 |
| 10 | Redis Cluster 一致性？| CP（Hash Slot + MOVED 重定向）+ 主从异步复制；W+R>N 保证写主读主强一致 |
| 11 | CAP 常见误区？| ① 选 CA 不选 P（错误！P 必选）② AP 不保证数据正确（不完全对！可调一致性）③ 2/3 投票 = 绝对强一致（错误！有不同强度）|
| 12 | CAP 经典论文？| Eric Brewer 2000 PODC；Gilbert & Lynch 2002 精确证明 |
| 13 | PACELC 论文？| Daniel Abadi 2012（MVCC for Cloud Computing） |
| 14 | 一致性强度分级？| Linearizable（最强，Raft Commit）→ Sequential → Causal → Monotonic Read（最弱）|
| 15 | TiKV 读的一致性强度？| Lease Read = Linearizable（最强）；ReadIndex = Sequential；本地读 = Monotonic Read |
| 16 | CAP 面试最高频？| ① P 必选原因 ② CP vs AP 典型系统 ③ 正常运行时 C vs L ④ TiKV/Nacos PACELC 分析 |
| 17 | 选型建议？| 金融/支付/账户 → CP（TiKV/Spanner）；服务发现/社交动态 → AP（Nacos Naming/Cassandra）|
| 18 | CAP vs BASE？| BASE = Basically Available（基本可用）+ Soft state（软状态）+ Eventually consistent（最终一致）；AP 系统的核心承诺 |
| 19 | CRDT 是什么？| Convergent Replicated Data Type（可收敛副本数据类型）→ AP 系统保证最终一致的核心算法（Nacos Distro/Cassandra）|
| 20 | CAP 学习路径？| 读 CAP 论文 → PACELC 论文 → TiKV/ETCD/Nacos 源码验证 → 理解一致性强度分级 → 实战选型 |
